## B. DATA FLOW MAP

### 1. INITIAL LOAD (Dashboard)
```
USER → login() → showApp() → loadData()
  → getDashboardData(token, adminFilter)
    → _getCacheChunked(cacheKey) → [HIT] return cached
    → [MISS]
      → SpreadsheetApp.getActiveSpreadsheet()
      → Master.getDataRange().getValues()           // 1 read: ALL master rows
      → Cubs.getDataRange().getValues()             // 1 read: ALL cubs rows
      → Families.getDataRange().getValues()         // 1 read: ALL families rows
      → Actions.getDataRange().getValues()          // 1 read: ALL actions rows
      → Interactions.getDataRange().getValues()     // 1 read: ALL interactions rows
      → EmailHistory.getDataRange().getValues()     // 1 read: ALL email history rows
      → ReadingCircle.getDataRange().getValues()    // 1 read: ALL RC rows
      → Orientation.getDataRange().getValues()      // 1 read: ALL orientation rows
      → RC_Pending.getDataRange().getValues()       // 1 read: ALL RC pending rows
      → Ori_Pending.getDataRange().getValues()      // 1 read: ALL Ori pending rows
      → In-memory: build maps, filter, transform, enrich
      → JSON.stringify(payload) → _putCacheChunked() → return
  → renderDashboard(), renderActionsTable(), etc.
```

### 2. NAVIGATION (Orientation Page)
```
USER clicks "Orientation" nav → handleRoute('#/orientation')
  → loadOrientationPage(force)
    → if cached (<5min) → _renderOriPage() from _oriData [INSTANT]
    → else getOrientationPageData(token)
      → _getCacheChunked(ori_page_KEY) → [HIT] return
      → [MISS]
        → Orientation.getDataRange().getValues()       // FULL read
        → Orientation_Pending.getDataRange().getValues() // FULL read
        → Cubs.getDataRange().getValues()              // FULL read (for cubName lookup)
        → Master.getDataRange().getValues()            // FULL read (for parentName)
        → return { pendingRows, trackerRows }
      → cache → _renderOriPage()
```

### 3. WRITE (submitInteractions)
```
USER submits interaction form → submitInteractionForm()
  → optimistic UI update (local arrays, _renderAll())
  → close drawer, show "Saving..."
  → scriptRunWithRetry(ctx => ctx.submitInteractions(token, [payload]))
    → _withScriptLock(fn) → LockService.getScriptLock().waitLock(30s)
      → Interactions.appendRow(batch)             // 1 write
      → Actions.appendRow(batch)                  // 1 write (if action required)
      → Cubs.getDataRange().getValues()           // 1 read (for cubRowMap)
      → Cubs.setValues(batch per affected cub)    // N writes (batched 3 cols each)
      → _bustAllDashboardCaches()                 // increments cache_version + ori_rc_version
    → success → confirm optimistic IDs with real IDs → _renderAll() → toast
```

### 4. SYNC (runDailySync - 6 AM daily)
```
Trigger → runDailySync()
  → _fetchEnrichmentData() [OUTSIDE LOCK]
    → SpreadsheetApp.openByUrl(B2) → Master.getDataRange().getValues()
    → SpreadsheetApp.openByUrl(B3) → Registry.getDataRange().getValues()
    → SpreadsheetApp.openByUrl(B3) → ScoreCalendar.getDataRange().getValues()
    → Local ReadingCircle.getDataRange().getValues()
    → Local Orientation.getDataRange().getValues()
  → _withScriptLock(() => {
      _updateOverdueActionsStatus()     // reads Actions, batch writes Overdue
      _runIncrementalSync()             // processes Master in chunks of 2000
        → mirror Master to local Master  // clear + setValues
        → _syncFamiliesBulk()            // read Families, build map, clear+setValues
        → _syncCubsBulk()                // read Cubs, build map, enrich, clear+setValues
        → _bustAllDashboardCaches()
      })
```

## E. CACHE AUDIT

### Current Cache Architecture
```
Cache Keys (Script Cache, 100KB limit per key, chunked at 90KB):
├── dash_cv7_v{version}_{role}_{name}          → Full dashboard payload (~80-150KB)
├── cover_cv6_v{version}                        → Cover actions (~20-50KB)
├── handover_hn1_v{version}                     → Handover notes (~10-30KB)
├── ori_page_ori1_v{ori_rc_version}             → Orientation page data (~30-80KB)
├── rc_page_rc1_v{ori_rc_version}               → RC page data (~30-80KB)
├── search_idx_cv5_v{search_cache_version}      → Master search index (~50-100KB)
├── form_init_data_v3                           → Dropdowns (~5-10KB)
├── access_list_v1 (60s TTL)                    → User credentials
├── tok_{token} (6h TTL)                        → Session tokens
└── SEEN_FAMS / SEEN_CUBS (10min TTL)           → Sync resume state
```

### Cache Version Strategy (Good)
- **Global version** (`cache_version`): Incremented on ANY write → busts all dashboard caches
- **Ori/RC version** (`ori_rc_version`): Incremented on Orientation/RC writes only → preserves dashboard cache
- **Search version** (`search_cache_version`): Incremented only on Master sync → preserves search index
- **CODE_VER constants** (`cv7`, `cv6`, `ori1`, `hn1`, `cv5`): Bumped on code deployment to invalidate stale caches

### Issues
| Issue | Severity | Description |
|-------|----------|-------------|
| **C1** | P1 | Dashboard payload often exceeds 100KB → chunking adds overhead (multiple `cache.get` calls). Consider splitting into `dash_stats`, `dash_actions`, `dash_interactions`, `dash_families`, `dash_cubs` |
| **C2** | P2 | `getDashboardData` caches per-role+name+filter. Admin with "All Reps" filter gets different cache than Admin with "Rep A" filter. Good. But Rep caches are per-rep. Could share base data + filter client-side. |
| **C3** | P2 | `getOrientationPageData` and `getRCPageData` use 5-min SWR on client but 5-min TTL on server. Server cache TTL should be longer (e.g., 10-15 min) with client SWR handling freshness. |
| **C4** | P1 | **No cache for cub detail data** (email history, full interaction history). Every drawer open calls `getInteractionsForCub` (no cache) + `getDashboardData` already has email history. Should cache email history per-cub. |
| **C5** | P3 | `_bustAllDashboardCaches` increments BOTH versions. Some writes (interactions, actions, families) don't affect Ori/RC data but still bust `ori_rc_version`. Fixed partially but `submitInteractions`, `deleteInteraction`, `editInteraction`, `submitHandoverNote` still call `_bustAllDashboardCaches`. |

## F. UI PERFORMANCE AUDIT

### Navigation & Page Loading
| Flow | Current Behavior | Problem | Recommendation |
|------|------------------|---------|----------------|
| **Dashboard → Orientation** | `loadOrientationPage()` fetches if cache >5min or force | 5-min TTL; full sheet reads on miss | Client has SWR (shows stale instantly, refreshes bg). Server TTL should be 10-15min. |
| **Dashboard → Reading Circle** | Same as above | Same | Same |
| **Orientation tab switch** (Pending ↔ Master ↔ Sessions) | Client-side filter on `_oriData` | ✅ Instant (no server call) | Good |
| **RC tab switch** (Pending ↔ Roster) | Client-side filter on `_rcData` | ✅ Instant | Good |
| **Drawer open (Cub/Family)** | Renders from `cubsList` / `familiesList` (already in memory) | ✅ Instant | Good |
| **Interaction Drawer search** | Local filter (cubsList) → then server `searchContacts(searchAll=true)` | Debounced 250ms; server searches full Master | Server search uses cached `searchableList` — good. Local filter first is excellent. |
| **Admin filter change** | Calls `loadData()` (full dashboard refetch) | 5-min cache helps; but sequence counter prevents race | Good pattern with `_loadDataSeq` |

### Rendering Performance
| Component | Rows | Render Method | Issue |
|-----------|------|---------------|-------|
| Dashboard Actions table | 50/page | `paginateAndRender` + `innerHTML` per row | Creates DOM per row; OK for 50 |
| Actions table (Engagements) | 50/page | Same | OK |
| Interactions table | 50/page | Same | OK |
| Cubs table | 50/page | Same | 21 columns × 50 rows = 1050 cells; OK |
| Families table | 50/page | Same | OK |
| Cover table | 50/page | Same | OK |
| Orientation Master table | 50/page | `innerHTML` via `.map().join('')` | String concat faster than DOM |
| RC Roster table | 50/page | String concat | Good |

**Issues:**
1. **F1 (P2)** — `lucide.createIcons({ nodes: [tbody] })` called after EVERY table render. Scans entire tbody for `data-lucide` attributes. With 50 rows × 5-10 icons = 250-500 icons per render. Acceptable but could be optimized by creating icons once per cell template.
2. **F2 (P3)** — `filterInteractions`, `filterCubs`, `filterCoverActions` re-filter entire arrays on every keystroke (debounced 200ms). Arrays are small (<3000) — fine.
3. **F3 (P1)** — **No virtual scrolling**. Tables render 50 rows via pagination. Good. But if user sets page size larger, DOM grows. Current PAGE_SIZE=50 is reasonable.

### State Management
```
Global State (App.html lines 19-75):
├── session                  // auth
├── dashboardData            // stats
├── actionList               // all actions (filtered per view)
├── interactionsList         // all interactions (split into my/guest)
├── familiesList             // all families
├── cubsList                 // all cubs (with readingCircle merged)
├── globalMasterSearchIndex  // search index (loaded async after loadData)
├── coverActionsList         // all reps' actions
├── handoverNotesList        // all notes
├── paginationState          // per-table page state
├── _loadDataSeq             // sequence counter for race prevention
└── formDropdowns            // dropdown options
```

**Issues:**
- **S1 (P2)** — `cubsList` is the "source of truth" for cub data. But `readingCircleList` and `orientationList` are ALSO in dashboard payload and merged into `cubsList` (line 895-901). Then `loadOrientationPage` and `loadReadingCirclePage` fetch SEPARATE datasets (`_oriData`, `_rcData`) that duplicate data. ## J. CONCURRENCY AUDIT

### Locking Strategy
- **Script-level lock** (`LockService.getScriptLock()`) used for ALL write operations via `_withScriptLock`
- Timeout: 30 seconds (increased from 10s)
- Client-side retry with exponential backoff (`scriptRunWithRetry`, max 3 retries)

### Race Conditions Identified
| Scenario | Protection | Gap |
|----------|------------|-----|
| Two reps submit interaction for same cub | Lock serializes; Cubs update uses `cubRowMap` built at lock start | If cub added between read and write, `cubRowMap` misses it → interaction skipped (logged warning). Acceptable. |
| Two reps update same Orientation row | Optimistic locking via `versionTs` (Last Updated column) | ✅ Good — throws conflict error |
| Two reps confirm same pending signup | Lock serializes; pending row deleted on confirm | ✅ Good |
| Sync running while user writes | Sync uses lock; user writes use lock | ✅ Serialized; user waits up to 30s |
| Form submit while sync runs | Form submit uses lock; sync uses lock | ✅ Serialized |

### Issues
- **CNC1 (P2)** — Lock held during `submitRCAttendance` full sheet rewrite (2-3s). Other writes queue. Fix W18 reduces lock hold time.
- **CNC2 (P3)** — No `LockService` for read operations. Stale reads possible but cached data mitigates.

## DETAILED CHANGE SPECIFICATIONS (Top 5)

### Change 1: Fix `submitRCAttendance` Full Sheet Rewrite
```
FILE: DashboardWrite.gs
FUNCTION: submitRCAttendance (lines 833-965)

CURRENT BEHAVIOR:
  1. Reads entire Reading Circle sheet into `data` array
  2. Adds new date column header if missing
  3. Loops all rows, updates attendance status in memory
  4. Recalculates No. Present / Last Attendance for ALL rows
  5. WRITES ENTIRE SHEET: `sheet.getRange(1, 1, data.length, headers.length).setValues(data)`
  6. Appends new rows for new cubs
  7. Loops attendanceMap again to propagate to Cubs tab (reads data again)

PROBLEM:
  - O(Rows × Cols) write every attendance submit
  - With 500 cubs × 20 date cols = 10,000 cells written
  - Lock held for 2-3 seconds
  - Triggers full recalculation of any dependent formulas

ROOT CAUSE:
  - Simpler to rewrite whole sheet than compute sparse updates
  - Dynamic date columns make sparse indexing harder

PROPOSED CHANGE:
  1. Keep reading full sheet (needed for recalc anyway)
  2. Track only CHANGED rows: `changedRows = []` where attendance changed
  3. For new date column: `sheet.getRange(1, dateColIdx+1).setValue(dateStr)` (1 cell)
  4. For changed rows: build `RangeList` of `{row, values: [newStatus]}` → `rangeList.setValues(...)`
  5. For new cubs: batch append as before
  6. Recalculate No. Present / Last Attendance ONLY for changed/new cubs
  7. Propagate to Cubs tab only for changed/new cubs

WHY FASTER:
  - Writes ~N cells instead of N×M (N=cubs, M=date columns)
  - Lock hold time drops from 2-3s to ~200-500ms
  - Eliminates quota pressure

RISKS:
  - Dynamic column indexing must be correct
  - RangeList has 30k cell limit per batch (well under)
  - Must handle header row (row 1) separately

DEPENDENCIES:
  - None

EXPECTED IMPACT:
  - submitRCAttendance: 2-3s → 300-500ms
  - Lock contention eliminated for concurrent attendance submits
  - Quota usage reduced 90%+
```

### Change 2: Split `getDashboardData` into Granular Endpoints
```
FILE: DashboardData.gs (new functions), App.html (loadData)

CURRENT BEHAVIOR:
  - Single `getDashboardData` reads 8 sheets, returns 500KB+ JSON
  - Cached as monolithic chunked payload
  - All pages (Dashboard, Engagements, Directory) wait for this one call

PROBLEM:
  - Dashboard tab only needs: stats, actions (50), families (50), cubs (50)
  - Engagements tab only needs: actions, interactions
  - Directory tab only needs: cubs, families
  - Orientation/RC pages have own loaders

ROOT CAUSE:
  - Historical monolith; easier to cache one payload

PROPOSED CHANGE:
  1. Create:
     - `getDashboardStats(token, filter)` → stats only (1 Master read for parent map + 1 Cubs read)
     - `getDashboardActions(token, filter)` → actions + interactions (2 reads)
     - `getDashboardCubs(token, filter)` → cubs list (1 Cubs read)
     - `getDashboardFamilies(token, filter)` → families list (1 Families read)
  2. `loadData()` calls these in PARALLEL via `Promise.all`:
     ```js
     const [stats, actions, cubs, families] = await Promise.all([
       call('getDashboardStats'),
       call('getDashboardActions'),
       call('getDashboardCubs'),
       call('getDashboardFamilies')
     ]);
     ```
  3. Each endpoint has own cache key: `dash_stats_v{ver}`, `dash_actions_v{ver}`, etc.
  4. `_bustAllDashboardCaches` increments version → all invalidate

WHY FASTER:
  - Parallel backend calls (GAS handles concurrent executions)
  - Each reads 1-2 sheets instead of 8
  - Smaller payloads → no chunking overhead
  - Client can render Dashboard stats instantly while Actions/Cubs load

RISKS:
  - More cache keys to manage
  - Sequence counter (`_loadDataSeq`) must handle multiple in-flight requests
  - Admin filter must be passed to all endpoints

DEPENDENCIES:
  - App.html `loadData` rewrite
  - Cache version strategy unchanged

EXPECTED IMPACT:
  - Cold dashboard load: 2-4s → 800ms-1.2s (parallel)
  - Cached load: 50ms → 20ms (smaller payloads)
  - Engagements/Directory pages load only what they need
```

### Change 5: Optimize `_autoMatch` Phone Index
```
FILE: FormHandler.gs
FUNCTION: _autoMatch (lines 247-307)

CURRENT BEHAVIOR:
  - For each cub in form response, loops ALL master rows
  - Cleans phone, compares against Parent Phone + Parent WhatsApp
  - O(M×N) where M=form cubs (1-5), N=master rows (500-2000)

  2. Then `_autoMatch` looks up `phoneMap.get(cleanPhone)` → O(1)
  3. Name matching still loops but only for phone-matched subset

WHY FASTER:
  - Phone match: O(N) → O(1) per cub
  - Form submit: 1-2s → 200-500ms

RISKS:

```
